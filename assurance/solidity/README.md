# Experimental checkpoint registry — local assurance only

MIT, optional developer experiment. **Not integrated with the broker runtime.** No deploy command, network RPC, wallet, private key, gas purchase or real-chain transaction is included. Never put raw audit events, credentials or personally identifying labels into this contract.

`AuditCheckpoint.sol` records opaque digest checkpoints from one immutable publisher and producer. A deployment-bound domain, a strictly increasing uint64 event sequence and the expected previous digest prevent accidental cross-deployment/cross-producer submissions, regressions and stale concurrent heads. Sequence gaps are deliberately allowed for batching: this is not evidence that all events exist. The authorized publisher can submit invented digests; a test demonstrates that limitation.

## Reproduce on Linux x86_64

Node22+, npm and an explicitly downloaded compiler are needed only for this experiment. Runtime Python dependencies are untouched. Install the isolated development dependencies from their integrity-pinned lockfile:

```sh
cd assurance/solidity
npm ci --ignore-scripts --no-audit --no-fund

solidity_tools=$(mktemp -d)
curl --fail --location --max-time 60 \
  'https://raw.githubusercontent.com/ethereum/solc-bin/gh-pages/linux-amd64/solc-linux-amd64-v0.8.37+commit.f401782d' \
  -o "$solidity_tools/solc"
printf '%s  %s\n' '5de843c2c93563cc66425c99a4fb13fdbf32b4c4ae07469480faaf126e14404a' "$solidity_tools/solc" | sha256sum --check -
chmod 700 "$solidity_tools/solc"
ASSURANCE_SOLC="$solidity_tools/solc" npm test
```

The compiler runner verifies the same pinned SHA256 before execution, bounds the compiler size/input/output/time and executes the verified open file descriptor on Linux. It does not automatically download anything. A checksum from the official HTTPS manifest pins an artifact; it is not an independently signed reproducible-build attestation. The file must be a single-link regular file owned by the current UID or trusted root, without group/world write permissions. Descriptor execution prevents pathname replacement; it does not freeze in-place writes by the same UID/root, which remain trusted. Trust in the toolchain and its host remains necessary. Do not commit downloaded tools, generated bytecode, node_modules or test artifacts.

The emulator uses Prague execution rules and a mock in-memory blockchain/state. Its synthetic caller addresses are injected directly by the test harness; no transaction signing keys or wallet authentication are tested. No testnet or mainnet is contacted or forked.

## Verified locally

- Official solc0.8.37+commit.f401782d, SHA256 above, binary15473648bytes, stored temporarily outside the repository.
- Actual compiled EVM bytecode executed through `@ethereumjs/evm`10.1.3; development dependency graph locked with npm integrity metadata (14installed packages).
- Eight EVM tests passed: valid/history preservation; caller/domain/producer/previous-head rejection; duplicate/backwards/zero-root rejection; seeded randomized sequence; invented-root limitation; zero constructor values; uint64/ABI boundaries; cross-deployment replay rejection.
- Randomized campaign: seed`0x4123`,256calls,84accepted and172rejected, with head/state assertions after every call and every historical digest checked at the end. This bounded campaign is **not exhaustive or a mathematical proof**. A ninth compiler-gate test rejects devices, oversized files, symlinks/hardlinks and wrong checksums before execution.

To attempt the Solidity CHC checker separately:

```sh
ASSURANCE_SOLC="$solidity_tools/solc" npm run smt
```

In this environment Z3/Eldarica were unavailable: diagnostics8158/7649, `status:solver-unavailable`, zero proven assertions, exit2. **No formal verification is claimed.** Installing/choosing a solver, proving the explicit assertions and separately reviewing the specification would be additional work. Even successful SMT checking would not verify vault isolation, cryptographic commitments, complete off-chain capture, EVM consensus or the whole Python broker.

## Publication and operational limits

The registry has no upgrades, publisher rotation, transfers or external contract calls. Losing the publisher key would stop future publication; compromising it would permit false future commitments, although prior finalized entries cannot be changed through this interface. A real deployment would need a separate reviewed key-custody/recovery policy and trusted identification of the chain, deployment and publisher. There is no automatic deployment integration.

Each append stores a historical mapping entry, so aggregate storage grows. One batch costs bounded contract work but actual chain fees, inclusion and finality vary. Nothing in this experiment measures or promises production fees. Forced ETH can still reach contracts without payable methods; this contract is not a funds custodian and has no withdrawal path.

Publishing a digest does not hide publisher addresses, batch cadence, sequence values or transaction ordering. Predictable input hashes can be guessed. Reorgs, censorship and finality assumptions affect what a verifier can rely on. See [assessment and alternatives](../../docs/solidity-assessment.md).

An optional CI job may run the commands above on an ephemeral Linux runner using only these fixtures and pinned artifacts. Keep it separate from the runtime's mandatory checks; it needs no secrets, wallet or RPC URL. The broker maintainer decides whether to enable it. This README does not claim that any Solidity GitHub job has run.
